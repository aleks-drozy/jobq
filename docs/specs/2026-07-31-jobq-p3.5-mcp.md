# jobq P3.5 — MCP Surface

Status: ratified 2026-07-31, built and green same day.

## Scope: why MCP now, reversing P3's own reasoning

P3's spec (`2026-07-30-jobq-p3-http.md`) deferred MCP with a specific
argument: stdlib-only is this repo's stated discipline, and without an
official Go SDK, an MCP server meant hand-rolling JSON-RPC 2.0 framing plus
the `initialize`/`tools/list`/`tools/call` handshake — a second protocol
project, not a bolt-on.

That argument is now stale, not wrong-in-hindsight. `github.com/modelcontextprotocol/go-sdk`
has shipped a v1 (v1.0.0), stabilized client OAuth (v1.5.0), and reached
v1.7.0 targeting MCP spec 2026-07-28 — a maintained, Google-affiliated SDK
with typed tool registration (`mcp.AddTool[In, Out]`), stdio and in-memory
transports, and JSON Schema inference from Go structs. Hand-rolling JSON-RPC
is no longer defensible with a working v1 SDK sitting in the module proxy.
P3.5 uses it: `github.com/modelcontextprotocol/go-sdk v1.7.0`.

## Prior art (WebSearch, 2026-07-30)

No Go-based job-queue MCP server was found. Searches for MCP surfaces over
Go queues (River, asynq, Faktory, Machinery) returned the queues themselves
and the Go MCP SDKs, not a repo joining the two — treated as "found none,"
not "none exists"; web search is weak evidence of absence.

Broker-wrapper MCP servers do exist, and this README does not pretend
otherwise: `kanapuli/mcp-kafka`, `aywengo/kafka-schema-reg-mcp` (Kafka),
`amazon-mq/mcp-server-rabbitmq` (RabbitMQ, multi-broker + OAuth), AWS's own
SQS/SNS server (tag-based mutation safety), and "Queue Pilot" (14+ tools,
unified Kafka/RabbitMQ adapter). The distinction that survives scrutiny:
every one of those is an MCP client adapter pointed at somebody else's
broker. The durability story belongs to Kafka/RabbitMQ/SQS; the MCP layer
forwards a vendor status API. In jobq the engine underneath is this
repository's own segmented, CRC'd WAL with deterministic replay and a
kill-the-process-cold harness (`crash_test.go`), so `jobq_recovery_report`
returns *this repo's* `RecoveryReport` from *this repo's* replay path. That
is the framing — not "first job-queue MCP server."

Sources: [modelcontextprotocol/go-sdk](https://github.com/modelcontextprotocol/go-sdk) ·
[mark3labs/mcp-go](https://github.com/mark3labs/mcp-go) (considered, rejected
below) · [River](https://github.com/riverqueue/river) ·
[asynq](https://pkg.go.dev/github.com/hibiken/asynq).

`mark3labs/mcp-go` is a viable community SDK but doesn't track MCP spec
versions the way the official SDK does; with an official v1 SDK available,
that's the one to build on.

## Nested module: why, not just "how"

`go-sdk` pulls 8 direct dependencies (`jsonschema-go`, `segmentio/encoding`,
`golang-jwt/v5`, `x/oauth2`, `x/tools`, `x/sync`, `x/time`,
`yosida95/uritemplate`). Adding those to the root `go.mod` would break the
root README's "standard library only" claim outright.

**Resolution:** `mcp/` is its own module (`module github.com/aleks-drozy/jobq/mcp`),
with a `replace github.com/aleks-drozy/jobq => ../` so it always builds
against the current checkout rather than requiring a tag bump on every
root-module change to pick it up (this is a mono-repo, not two independently
released projects). The engine, WAL, recovery, `jobqhttp`, `cmd/jobqd`, and
`cmd/jobq` remain provably stdlib-only — `go list -m all` in the root module
is the proof, and CI now asserts it (see below) instead of trusting the
README sentence. The MCP adapter is explicitly a *consumer* of the jobq
library, which is what it is.

## The one genuinely new engine primitive: `Peek`

Every one of the five lifecycle tools (`enqueue`/`dequeue`/`ack`/`nack`/`extend`)
is a direct pass-through onto `jobq.Client`, free since P3. `list_topics`,
`topic_stats`, `health`, `recovery_report` are free too — `jobqhttp.Client`
already had `Topics`/`TopicStats`/`Stats`/`Health`/`Recovery`. One tool in
the pre-scoped P3.5 list was not free, and building it the obvious way would
have been a correctness trap: **`dlq_peek`**.

`topic.go`'s `dequeue` case does `job.Attempts++` unconditionally — it's the
engine's *only* other read path into a topic, and it's not read-only.
`queue.go`'s `retire` has no onward queue for a job already inside a `.dlq`:
attempts exhausted there means the job is destroyed, counted in
`Stats.Dropped`. A DLQ job gets `DefaultMaxAttempts = 5`. So "peek the DLQ"
implemented as dequeue-then-nack burns one attempt **per look** — five
"just checking" look burns the whole budget and the job is gone, silently
correct-looking (`Dropped` increments, nothing panics) but destroyed
evidence. Handing that operation to an LLM that might call it repeatedly
while deciding what to do is not acceptable.

So P3.5 adds `Queue.Peek(topic string, limit int, includeInflight bool) ([]*Job, []*Job, error)`:
a new actor-loop case in `topic.go` that runs `expire()` (same discipline as
`stats`) then deep-copies up to `limit` jobs off the head of `ready` (and
the in-flight set if asked) — no `Attempts++`, no lease, no WAL record.
~30 lines in the actor, matching the estimate. Tests
(`peek_test.go`, root module): peek never mutates `Attempts`; peek then
dequeue delivers the same job at `Attempt == 1`; peek is FIFO-ordered and
preserves `NotBefore` on delayed jobs rather than filtering them out; peek
of a DLQ job preserves `DeadLetteredAttempts`/`DeadLetteredAt`; mutating a
peeked job's payload slice cannot corrupt queue state; an unknown topic
reports empty, matching `Stats`; `includeInflight` is opt-in and leaks
nothing when false.

`Peek` stays **outside** `jobq.Client`, for the same documented reason
`Stats`/`Topics` are: the local version cannot fail, the HTTP one can. It
mirrors that asymmetry rather than hiding it.

## HTTP surface for Peek

`GET /v1/topics/{topic}/jobs?limit=N&include_inflight=bool` →
`200 {"ready":[jobDTO],"inflight":[jobDTO],"truncated":bool}`. `limit`
defaults to 10, caps at 100 server-side, `400 bad_request` on a garbage
value. `jobqhttp.Client.Peek` fetches `limit+1` internally and trims to
derive `Truncated` — see "a small, deliberate signature asymmetry" below.
`jobqhttp/peek_test.go` runs the same assertions against a local `*jobq.Queue`
and a live `httptest` server, the same parity discipline `roundtrip_test.go`
established for the five `jobq.Client` methods in P3.

### A small, deliberate signature asymmetry

`jobq.Queue.Peek` cannot fail and reports no `Truncated` flag — it has
nothing to compare against without extra bookkeeping the actor loop doesn't
otherwise need. Widening it to return one anyway, just to look symmetric
with the HTTP/MCP layer, would mean the engine tracking state purely for a
transport concern. Instead, both `jobqhttp`'s `handlePeek` and the MCP
module's `localBackend.Peek` fetch `limit+1` jobs and trim the last one off,
turning "there was one more than fit" into `Truncated` without touching the
engine's own signature. `jobqhttp.Client.Peek` and the MCP `Backend.Peek`
both report `(ready, inflight []*jobq.Job, truncated bool, err error)` — the
four-value shape only exists at boundaries that can actually fail or
truncate.

## The MCP module

`Backend` is `jobq.Client` plus the inspection surface `jobqhttp.Client`
already had, plus `Peek`. `*jobqhttp.Client` satisfies it outright
(`var _ Backend = (*jobqhttp.Client)(nil)` in `server.go`); `localBackend`
adapts a `*jobq.Queue`, manufacturing the nil errors a local call can
honestly return where a network call cannot. `server_test.go`'s
`TestToolSuite` runs the entire tool behaviour suite twice — once per
backend — so the MCP surface cannot behave differently embedded vs. remote,
carrying P3's parity discipline one layer further up the stack.

`cmd/jobq-mcp` flags: `-addr` (default `http://127.0.0.1:8080`, env
`JOBQ_ADDR`) is the default mode; `-dir` opens an embedded durable queue and
is mutually exclusive with `-addr` (`flag.Visit` detects which were
explicitly set, since `-addr` always has a default value present); `-dir`
takes the same directory lock `jobqd` does, so pointing it at a directory
with a running `jobqd` fails with an explanatory message ("cannot share a
directory with a running jobqd; point -addr at it instead") rather than a
raw `jobq.lock` error. `-max-wait` (10s, below typical MCP client tool-call
timeouts) and `-max-payload` (256 KiB, a quarter of `jobqd`'s own 1 MiB
default — a payload that size from an LLM is a mistake, not a use case).
`-read-only` registers only the read-only tools.

**Decision: writes on by default.** The whole point of this surface is an
agent that can diagnose *and act on* a crash — see the demo. `-read-only` is
the documented, one-flag way to point this at anything real without that
risk; the README says so plainly rather than assuming the safer default and
leaving the capability undiscoverable.

### Tool schemas: struct inference, not hand-written JSON Schema

The official SDK's schema inference (`github.com/google/jsonschema-go`)
reads Go struct types via reflection: property names from `json` tags, a
plain-text description from the `jsonschema` tag, and **required** from
whether a field is `omitempty`. It does not support `minimum`/`maximum`/
`default`/`enum` via struct tags — the tag holds one string, the
description. Rather than hand-writing a parallel `*jsonschema.Schema` tree
per tool (11 of them) to get literal `minimum`/`maximum` keywords into the
wire schema, P3.5 lets the SDK infer type + required + description from the
Go struct — the single source of truth stays the Go code — and enforces the
numeric bounds (`limit` 1–100, `by_ms` > 0, etc.) in the handler, returning
the same stable `code` either way. A model reads the bound from the
description text either way; a strict client-side JSON-Schema validator
would not reject an out-of-range `limit` before the call reaches the
server, but the server does. This is a real, documented trade, not an
oversight.

### Errors: JSON-in-text, not `StructuredContent`

`mcp.AddTool`'s generated wrapper treats a non-nil `error` return specially:
it builds a **fresh** `CallToolResult` via `SetError(err)` and discards any
result value the handler also returned. There is no way to attach a typed
`code` field to `StructuredContent` on the error path without fighting that
wrapper. `errors.go` instead defines `toolError{Code, Message}` whose
`Error()` method returns its own JSON encoding, so the text content of an
error result is `{"code":"unknown_lease","message":"…"}` — parseable
by a test (or a model) without inventing a second, undocumented channel.
`jobq.ErrNoJob` is deliberately never passed through this path: every
handler that can see it checks first and returns `{"empty": true}` as a
normal, successful output.

### Read-only tool count: 5, not "6"

Five tools carry `readOnlyHint: true`: `jobq_peek`, `jobq_list_topics`,
`jobq_topic_stats`, `jobq_health`, `jobq_recovery_report`. (An earlier draft
of this plan's test list said "6 under `-read-only`" in one place while its
own tool-annotation table listed exactly five read-only tools in another —
an internal inconsistency in the plan, not a design question. This spec and
the shipped code follow the five-tool table; `server_test.go`'s
`TestToolListCounts` pins 11 total / 5 under `-read-only`.)

## Tool table

| Tool | Read-only? | One-line contract |
|---|---|---|
| `jobq_enqueue` | no | creates the topic on first use; `.dlq`-suffixed names rejected |
| `jobq_dequeue` | no | **consumes one attempt**; `wait_ms` long-polls (HTTP backend: server-side; local: in-process ticker) |
| `jobq_ack` | no | second ack on a settled lease → `unknown_lease` |
| `jobq_nack` | no | consumes an attempt; may dead-letter the job |
| `jobq_extend` | no | only lengthens a lease |
| `jobq_peek` | **yes** | no lease, no attempt, no log write |
| `jobq_list_topics` | **yes** | split into topics / dlq_topics |
| `jobq_topic_stats` | **yes** | omit `topic` for every topic; unknown topic = zeroes |
| `jobq_dlq_requeue` | no | compound: dequeue→enqueue→ack, never ack-first |
| `jobq_health` | **yes** | status, durable, uptime, mode |
| `jobq_recovery_report` | **yes** | process-start snapshot + deterministic `interpretation` |

Full JSON shapes and the payload/error encoding policy are in
[`mcp/README.md`](../../mcp/README.md), not duplicated here.

## `jobq_dlq_requeue` ordering, in detail

Per job: **dequeue-from-DLQ → enqueue-to-source → ack-the-DLQ-lease**, never
ack-first. A fault between the enqueue and the ack (process death, backend
timeout) leaves the DLQ lease to expire; the job is redelivered there —
a duplicate, which jobq's at-least-once contract explicitly permits.
Ack-first would risk the opposite: the DLQ copy gone, the enqueue to source
never having happened, an outright loss. `server_test.go`'s
`TestDLQRequeueOrdering` proves this with a `Backend` wrapper that injects
an `Ack` failure and asserts the pre-fault `Enqueue` was not rolled back.

Selecting specific jobs via `job_ids` (from a prior `jobq_peek`) costs
something the interface can't hide: the engine has no dequeue-by-ID, so
scanning past a job not in the set means taking it off the head and
`Nack`-ing it back — one attempt spent on a job the caller didn't ask to
touch. Documented in the tool description and in `mcp/README.md`, not
silently absorbed.

## Demo: the agent diagnoses a crash it did not witness

`mcp/demo/main.go` builds real `jobqd`/`jobq-mcp` binaries, seeds a real
queue (6 poison jobs dead-lettered for real before the crash, 5 jobs left
leased at kill time, 30 ordinary jobs mixed acked/ready), kills `jobqd`
**cold** (`Process.Kill`), clears the stale lock file the cold kill leaves
behind (documented, on-purpose behavior of `acquireDirLock`), restarts it,
then drives a **real** `sdk.Client` over a **real** `jobq-mcp` subprocess
through the diagnosis sequence: `jobq_health` → `jobq_recovery_report` →
`jobq_list_topics`/`jobq_topic_stats` → `jobq_peek` the DLQ → partition by
`dead_lettered_at` (zero = crash victim, non-zero = failed for real before
the crash) → `jobq_dlq_requeue` the crash victims only → a lease-expiry
redelivery check → a closing reconciliation
(`enqueued == acked + ready + in_flight + dead_letters + dropped`) computed
from real numbers and asserted, not printed on faith.

One real captured run lives in `mcp/demo/transcript.txt`. From that run: 5
crash-victim jobs correctly identified by a zero `dead_lettered_at`, all 5
requeued, the 6 real poison jobs left untouched in the DLQ, redelivery
confirmed post-recovery (`attempt: 2` after the lease expired), and the
closing reconciliation held exactly (`enqueued=26`,
`acked+ready+in_flight+dead_letters+dropped=26`). Numbers will differ on
your machine (different job IDs, timestamps, and a random free port) — the
shape will not.

A caveat surfaced by actually running this, recorded honestly rather than
smoothed over: `Stats.Enqueued` is not a cumulative all-time counter. Each
topic actor seeds it from the jobs replay restored
(`stats.Enqueued = len(ready)` in `topic.go`), then counts forward from
there — so `jobq_topic_stats` right after a restart reports "what's live in
this process's lifetime," not "everything ever enqueued." The demo's
reconciliation still holds exactly under that definition; it would be wrong
to read a post-restart `enqueued` count as full history.

## What P3.5 still doesn't do (honest list)

- No streaming/progress tool calls — every tool is one request, one
  response.
- `-read-only` is process-wide, not per-tool-call; there is no per-request
  authorization layer (matches jobqd having none — see P3's security note).
- `jobq_dlq_requeue`'s `job_ids` selection burns an attempt on jobs it scans
  past but doesn't select, because the engine has no dequeue-by-ID. Fixing
  that would mean a new engine primitive beyond `Peek`, out of scope here.
- No purge/delete/drain-all tool, and none is planned — the engine has no
  such primitive, and adding a destructive one whose only consumer is an
  LLM was rejected as a trade, not overlooked.
- The demo's agent trajectory is a scripted sequence of real tool calls
  against a real crash, not an actual LLM in the loop (see
  `mcp/demo/README.md`, "What isn't simulated") — reproducibility over
  spectacle.
- Nested-module CI (root `go list -m all` zero-dependency assertion, `mcp/`
  running its own `gofmt`/`vet`/`test -race` job) is described below; it
  has not yet been exercised on an actual CI run at time of writing this
  spec, only locally.

## CI

`.github/workflows/ci.yml` gets a second job, `mcp`, running
`gofmt -l . && go vet ./... && go test -race -count=1 ./...` with
`working-directory: mcp`. The root `test` job gains one step:
`go list -m all` must print exactly `github.com/aleks-drozy/jobq` — turning
"standard library only" from a README sentence into something CI actually
checks.
