# jobq P3 — HTTP Surface, CLI, and Why Not MCP Yet

Status: ratified 2026-07-30, built and green same day. **Superseded on the
MCP question by P3.5** (`docs/specs/2026-07-31-jobq-p3.5-mcp.md`) the next
day: the "not yet" below held for about 24 hours, until the official
`modelcontextprotocol/go-sdk` reaching v1 made the hand-rolled-JSON-RPC
argument stale. The `jobq.Client` seam this spec describes is exactly what
P3.5 built on.

## Scope decision: HTTP + CLI this pass, MCP as a designed seam

**MCP is out of scope for this pass.** Reasoning:

- Stdlib-only is this repo's stated discipline (README: "standard library
  only", zero deps in `go.mod`). An MCP server therefore means hand-rolling
  JSON-RPC 2.0 framing plus the `initialize` / `tools/list` / `tools/call`
  handshake and protocol-version negotiation over stdio. That is a second
  protocol project, not a bolt-on, and a shaky MCP surface is worse signal
  than none.
- The HTTP+CLI core is already four new packages/binaries plus a full test
  suite — a complete, focused pass on its own.
- A systems reviewer looking at a durable queue expects a service surface
  and a worker CLI. MCP is a bonus on top; shipping it over a half-built
  core would invert the signal.

**The seam that makes MCP nearly free later** is `jobq.Client` (`client.go`
in the `jobq` package): five lifecycle methods — `Enqueue`, `Dequeue`,
`Ack`, `Nack`, `Extend` — signature-identical to `*Queue`'s own, so a future
`cmd/jobq-mcp` is a thin tool-call → interface adapter with no new queue
logic. A pre-scoped P3.5 tool list: `enqueue`, `dequeue`, `ack`, `nack`,
`extend`, `topic_stats`, `list_topics`, `dlq_peek`, `recovery_report`.

## Package structure

```
jobq/                          package jobq — engine, WAL, recovery (unchanged)
  client.go                    the jobq.Client interface (5 methods)
  jobqhttp/
    wire.go                    request/response DTOs + error envelope, shared by server & client
    errors.go                  sentinel <-> HTTP status/code mapping, both directions
    handler.go                 NewHandler(q *jobq.Queue, opts ...HandlerOption) http.Handler
    handler_dequeue.go         dequeue + bounded long-poll
    client.go                  Client (implements jobq.Client) — talks to a jobqd
    doc.go
    handler_test.go
    client_test.go
    roundtrip_test.go          same-behaviour tests run twice: in-process Queue vs HTTP Client
    conservation_test.go       concurrent HTTP workers, -race, job conservation
    restart_test.go            enqueue over HTTP -> Close -> Open -> job still there
    lease_expiry_test.go       redelivery over HTTP, driven by a manual clock
  cmd/
    jobqd/main.go               server daemon
    jobqd/main_test.go
    jobq/main.go                CLI dispatch
    jobq/commands.go            one func per subcommand
    jobq/work.go                the `work` loop (long-poll -> exec -> ack/nack)
    jobq/format.go               stats/job table rendering
    jobq/commands_test.go
    jobq/work_test.go
  docs/specs/2026-07-30-jobq-p3-http.md   this file
```

Server and client live in **one** package (`jobqhttp`) so the wire types are
declared exactly once — no DTO duplication, and a wire change cannot desync
the two sides. Package name follows the `foo/foohttp` convention so imports
read `jobqhttp.NewHandler`.

The CLI is **HTTP-only, never local-dir**. `Open` takes an exclusive
directory lock (`acquireDirLock`), so a CLI opening the daemon's data dir
would fail anyway. One code path, and the failure mode is explained rather
than hit.

## `jobq.Client` (`client.go`, package `jobq`)

```go
type Client interface {
    Enqueue(topic string, payload []byte, opts ...EnqueueOption) (string, error)
    Dequeue(topic string, visibility time.Duration) (*Job, Lease, error)
    Ack(lease Lease) error
    Nack(lease Lease) error
    Extend(lease Lease, d time.Duration) (time.Time, error)
}
var _ Client = (*Queue)(nil)
```

These five signatures match `*Queue`'s exactly, so the HTTP client reuses
`jobq.WithDelay` / `jobq.WithMaxAttempts` verbatim instead of redeclaring
them.

`Stats` and `Topics` are deliberately **outside** the interface:
`Queue.Stats(topic) Stats` cannot fail, the HTTP version can (timeout,
connection refused, server error), and widening the in-process signature to
`(Stats, error)` to force symmetry would be a lie about the local case.
`jobqhttp.Client` exposes `TopicStats`/`Stats`/`Topics`/`Health`/`Recovery`
as extra methods instead, documented in `jobqhttp`'s package doc.

## HTTP API surface

Routing uses stdlib `http.ServeMux` method+wildcard patterns (Go 1.22+), so
`POST /v1/topics/{topic}/jobs` + `r.PathValue("topic")` needs no router
dependency, and a path matched under the wrong method yields an automatic
`405` with `Allow`.

| Method + path | Body | Success | Notes |
|---|---|---|---|
| `POST /v1/topics/{topic}/jobs` | see below | `201` `{"id":"…"}` | enqueue |
| `POST /v1/topics/{topic}/dequeue` | `{"visibility_ms":int,"wait_ms":int}` | `200` `{"job":{…},"lease":{…}}` / `204` | `204` = nothing ready |
| `POST /v1/topics/{topic}/leases/{leaseID}/ack` | — | `204` | |
| `POST /v1/topics/{topic}/leases/{leaseID}/nack` | — | `204` | |
| `POST /v1/topics/{topic}/leases/{leaseID}/extend` | `{"by_ms":int}` | `200` `{"deadline":"RFC3339Nano"}` | |
| `GET /v1/topics` | — | `200` `{"topics":[…]}` | sorted; includes `.dlq` topics |
| `GET /v1/topics/{topic}/stats` | — | `200` `Stats` | unknown topic = zeroes, per engine |
| `GET /v1/stats` | — | `200` `{"topics":{name:Stats}}` | whole-queue snapshot |
| `GET /v1/health` | — | `200` `{"status":"ok","durable":bool,"uptime_ms":n}` | |
| `GET /v1/recovery` | — | `200` `{"report":RecoveryReport,"started_at":…,"dir":…,"sync":"always"}` | process-start snapshot |

**Leases need no request body.** `Queue.Ack`/`Nack`/`Extend` read only
`Lease.Topic` and `Lease.ID`, so the URL carries everything the engine
consumes; the handler reconstructs `jobq.Lease{ID: leaseID, Topic: topic}`.
`Deadline`/`JobID` are advisory-only client-side data and never trusted over
the wire.

**Enqueue body — content-type decides:**
- `Content-Type: application/json` → `{"payload": <base64>, "delay_ms": int, "max_attempts": int}`.
- any other content type → the raw request body **is** the payload, with
  `?delay_ms=&max_attempts=`. This is what makes the API curl-demoable.

**No DLQ-specific endpoints.** A dead-letter queue is an ordinary topic
named `{topic}.dlq`, consumed through every endpoint above.
`POST /v1/topics/x.dlq/jobs` returns `400 reserved_topic`, straight from
`ErrReservedTopic`.

**Long-poll** (`wait_ms`, default 0, server-capped by `-max-wait`) is a
bounded retry loop over `Queue.Dequeue` with a ~25ms ticker plus
`r.Context()` cancellation. It touches no engine internals and is
documented as polling, not a notification path (`jobqhttp` package doc).

**Error envelope**, one shape everywhere:
`{"error":{"code":"unknown_lease","message":"…"}}`.

| Engine error | Status | `code` |
|---|---|---|
| `ErrNoJob` | `204` (no body) | — |
| `ErrUnknownLease` | `404` | `unknown_lease` |
| `ErrEmptyTopic` | `400` | `empty_topic` |
| `ErrReservedTopic` | `400` | `reserved_topic` |
| `ErrNonPositiveDuration` | `400` | `non_positive_duration` |
| `ErrClosed` | `503` | `closed` |
| malformed JSON / bad param | `400` | `bad_request` |
| body over limit | `413` | `payload_too_large` |

`404` for `ErrUnknownLease` is chosen because the engine deliberately makes
forged, settled, and expired leases indistinguishable; one status for all
three preserves that property instead of leaking which case occurred.
`errors.go` maps in **both** directions (`sentinelTable` /
`codeToSentinel`), so `jobqhttp.Client` returns the real sentinels and
`errors.Is(err, jobq.ErrNoJob)` works identically against a local `*Queue`
and a remote client — pinned by `roundtrip_test.go`.

Hard limits, all handler options: `WithMaxPayload` (default 1 MiB, enforced
with `http.MaxBytesReader`), `WithMaxWait` (30s), `WithMaxVisibility` (24h),
`WithLogger`. Unknown JSON fields rejected via `Decoder.DisallowUnknownFields`.
No auth (README lists it under "Not in v1"); `jobqd` defaults to binding
`127.0.0.1` and says why in its own doc comment.

### A routing edge case, documented rather than special-cased

An empty `{topic}` path segment (`POST /v1/topics//jobs`) collapses to a
double slash that `http.ServeMux` never routes to any pattern — the request
404s from the mux itself before `jobq.ErrEmptyTopic` could ever be produced,
and the response is the mux's plain-text 404, not the JSON error envelope.
`jobqhttp.Client.Enqueue` checks for an empty topic itself and returns
`jobq.ErrEmptyTopic` without a request, so Go callers see the same error as
a local `*jobq.Queue` (this is what makes `roundtrip_test.go`'s empty-topic
case pass identically both ways). A raw HTTP caller constructing that URL
by hand sees the mux's 404 instead — a routing artifact, not a bug to work
around with a second route just for it. Documented in `jobqhttp`'s package
doc.

## CLI (`cmd/jobq`)

Stdlib `flag` with per-subcommand `FlagSet`s — no cobra. Global:
`--addr` (default `http://127.0.0.1:8080`, env `JOBQ_ADDR`), `--timeout`,
`--json`; all three are bound into every subcommand's own `FlagSet` too, so
they may appear before or after the subcommand name.

```
jobq enqueue [--payload <str> | --file <path>] [--delay 5s] [--max-attempts 3] <topic> [-]
jobq dequeue [--visibility 30s] [--wait 10s] <topic>
jobq ack     <topic> <leaseID>
jobq nack    <topic> <leaseID>
jobq extend  --by 30s <topic> <leaseID>
jobq stats   [--json] [topic]
jobq topics
jobq health
jobq recovery
jobq work    [--visibility 30s] [--wait 20s] [--max-jobs N] <topic> -- <cmd> [args...]
```

**Flags precede positional arguments.** This is a real constraint of Go's
stdlib `flag` package (parsing stops at the first non-flag token, unlike
getopt-style CLIs), not a stylistic choice — `jobq dequeue work --wait 10s`
does not work; `jobq dequeue --wait 10s work` does. Documented in the CLI's
own `-h` output rather than papered over with a bespoke arg-reordering
parser, which would be exactly the kind of dependency-shaped complexity the
zero-dependency rule exists to avoid.

Durations use `time.ParseDuration` (`5s`, `1m30s`), converted to the API's
`_ms` integers at the boundary.

`jobq work` is the centerpiece and the answer to "there is no runnable
demo": long-poll dequeue → run `<cmd>` with the payload on **stdin** and
`JOBQ_JOB_ID` / `JOBQ_TOPIC` / `JOBQ_ATTEMPT` / `JOBQ_MAX_ATTEMPTS` in the
environment → **exit 0 acks, non-zero nacks**. Point it at a script that
fails on purpose and watch retries burn the attempt budget and the job land
in `emails.dlq`, live, in a terminal. It handles SIGINT/SIGTERM by nacking
the in-flight job instead of abandoning it to lease expiry (`runOneJob` in
`work.go`).

Exit codes: `0` success, `1` error, `2` usage, `3` no job available (so
`dequeue` is scriptable in a shell loop).

## Server (`cmd/jobqd`)

Flags: `-addr 127.0.0.1:8080`, `-dir` (empty ⇒ in-memory `jobq.New()`),
`-sync always|interval|never`, `-sync-every`, `-max-payload`, `-max-wait`,
`-shutdown-timeout`.

On start it logs the `RecoveryReport` returned by `Open`; `GET /v1/recovery`
serves the same snapshot afterwards, named `started_at` rather than "now" so
it cannot be misread as live health.

**Shutdown ordering is a correctness point, not boilerplate**
(`serve` in `main.go`): on SIGINT/SIGTERM, `srv.Shutdown(ctx)` **first**
(stop accepting, drain in-flight requests), **then** the caller's deferred
`q.Close()`. Reversed, in-flight handlers would fail with
`ErrClosed`/`503`; in this order `Close` also gets to write the
`CLEANSHUT` record, so the next `Open` reports a clean shutdown rather than
a torn tail. `serve()` is factored out from flag parsing specifically so
this ordering is testable against a real `net.Listener` and a
caller-controlled `context.Context`, without fighting OS signal delivery in
a test (`TestServeShutdownOrdering`).

## Test plan (what actually shipped)

1. **`handler_test.go`** — table tests per endpoint: every status/code row
   in the API table, both enqueue content types, `413` on oversize, `405`
   on wrong method, unknown-field rejection, health durable/not-durable.
2. **`roundtrip_test.go`** — the headline test. One behaviour suite,
   executed twice against `jobq.Client`: once as `*jobq.Queue`, once as
   `*jobqhttp.Client` against a live `httptest` server. Any divergence in
   sentinel errors, attempt counting, or DLQ routing fails the build.
3. **`conservation_test.go`** — 8 producer + 8 consumer + 4 DLQ-consumer
   goroutines over real HTTP against one in-memory queue, under `-race`;
   every enqueued job is accounted for as exactly one ack (main topic or
   after dead-lettering), asserted via `Queue.Stats` plus a duplicate-ack
   guard.
4. **`restart_test.go`** — `SyncAlways` on a temp dir, enqueue over HTTP,
   `Close`, reopen, assert `CleanShutdown`/`JobsRestored`, and that the job
   is still dequeuable and ackable over a fresh HTTP server on the reopened
   queue.
5. **`lease_expiry_test.go`** — redelivery over HTTP driven by
   `jobq.WithClock`, not sleeps: `Attempt` increments on redelivery, and the
   original (now-superseded) lease correctly refuses to settle a second
   time.
6. **`cmd/jobqd/main_test.go`** — flag defaults (must default to
   `127.0.0.1`, never `0.0.0.0`), unknown `-sync` rejected, and
   `TestServeShutdownOrdering` proving requests are drained before the
   queue closes.
7. **`cmd/jobq`** — `resolvePayload` and `formatStatsTable` as pure,
   table-tested functions; end-to-end subcommand tests against a live
   `httptest` server (enqueue/dequeue/ack round trip, exit codes 0/1/2/3,
   both flag orderings); `work_test.go` reuses the crash-harness's
   self-exec pattern (a `TestMain` gate) to run the compiled test binary
   itself as the wrapped `<cmd>`, covering ack-on-success,
   nack-then-dead-letter-on-failure, and SIGINT-nacks-the-in-flight-job.

Gate before every commit: `gofmt -l .` empty (on the actual git blob, not
the CRLF-converted Windows working tree — see below), `go vet ./...`,
`go test -race -count=1 ./...`.

### A Windows environment note, not a P3 finding

This machine has `core.autocrlf=true`, so the local working tree checks out
`ack_durability_test.go`, `audit_test.go`, and `job.go` (all pre-existing,
untouched by P3) with CRLF line endings, and local `gofmt -l .` flags them
for that reason alone. The actual git blobs (`git show HEAD:<file>`, which
bypasses the checkout filter) are LF and gofmt-clean, matching what CI
(`ubuntu-latest`, checked out with LF) has always seen. Every file P3 added
was verified gofmt-clean directly. Not a P3 regression; recorded here so a
future reader on this machine doesn't mistake it for one.

## What P3 still doesn't do (honest list)

- No authentication — `jobqd` binds `127.0.0.1` by default specifically
  because of this.
- Long-poll is polling (~25ms ticker), not a push/notification path.
- `GET /v1/recovery` is a process-start snapshot, not live state.
- No MCP surface yet — see the scope decision above; `jobq.Client` is the
  seam that makes it cheap when it happens.
- No TLS, no rate limiting, no per-topic auth — all out of scope for a
  single-node, no-auth v1 daemon.
